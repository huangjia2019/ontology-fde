# FDE 实践：把退款业务转成程序中的判断

客户说遥控器无法配对，客服查到订单已签收，视频也符合证据要求，ERP 却没有返回发票。可能是未开票，也可能是同步延迟或查询条件不对。工程师要和财务确认：什么材料能证明未开票，由谁提供。

[退款走查记录](artifacts/01-field-walkthrough.md)列出了这笔申请在各系统中的记录与查询结果。

## 从人工操作找出缺失的定义

客服可能会说：“金额不大，问一下财务就能退。”这句话里藏着几个程序无法直接使用的约定。“不大”在项目中定义为不超过 500 元；“问一下财务”要取得明确的发票状态；“能退”还要区分批准申请、创建付款指令和资金到账。

把这笔业务完整跟一遍，可以找到需要补充的定义。若只收集退款政策文档，就容易漏掉财务查询、编号核对和失败后的实际处理。

```bash
python3 run.py inspect YF-R-0311
```

输出中 `invoice_status` 为 `unknown`，来源保留 ERP 的 `not_found`。可以据此和财务讨论：什么材料足以确认未开票，确认记录保存在哪里，确认后是否需要重新检查其他条件。

## 从判断条件推导模型

自动批准需要确认退款商品，因此申请必须关联订单项。需要确认交易已履约，因此要取得订单状态。批准与付款指令分别记录后，指令创建失败时可以保留批准结果，财务继续核查付款故障；重试前也能查询是否已有指令，避免重复创建。

```text
业务条件：只能退这位客户在这笔订单中购买的商品
  → 对象：客户、订单、订单项、退款申请
  → 引用：申请中的 customer_id、order_id、order_item_id
  → 检查：订单属于该客户，订单项属于该订单
  → 失败处理：引用不一致时拒绝拼接事实
```

若一个字段不会影响当前判断、操作或交接，可以暂缓接入；若缺失字段会改变处理结果，就必须定义其来源和缺失时的行为。

[第 4 站](artifacts/04-minimum-ontology.md)给出了对象与状态的完整推导，[来源映射](../config/ontology/source_map.yaml)记录字段与源系统的对应关系。

## 用相近案例检查设计

只看正常申请，很难发现授权和规则中的遗漏。可以比较以下样例：

| 案例差异 | 应发生的变化 | 检查的设计 |
|---|---|---|
| 500 元变成 500.01 元，其他条件满足 | 自动批准变为人工审批 | 金额上限和人工路径 |
| 金额不变，执行者换成未登记 Agent | 拒绝执行，申请状态不变 | 动作主体授权 |
| 条件全部通过，但创建付款指令失败 | 进入待付款状态，产生财务任务 | 补偿和人工接手 |
| ERP 未返回发票记录 | 保留未知状态，转人工核实 | 来源语义和缺失值处理 |

```bash
python3 run.py run YF-R-0500 --mode write
python3 run.py run YF-R-0501 --mode write
python3 run.py run YF-R-0500 --mode write --actor agent.marketing.unknown
python3 run.py run YF-R-0800 --mode write --simulate-payment-failure
```

比较 `rule_hits`、`state_after` 和 `actual_effect`，能够知道差异在哪一步产生。每次运行命令，程序都会重新读取样例文件。第一条命令批准了 `YF-R-0500`，但修改只保存在那次运行的内存中。因此，第三条命令再次处理它时，申请仍为 `pending_review`，可以在相同业务条件下比较不同执行者的结果。

## 人工接手怎样减少重复劳动

`YF-R-0610` 的一般退款检查已通过，但风控要求复核。审批材料 HAP-0610 保存申请编号、金额和转人工原因；对象、证据引用、已通过的检查和候选意见保存在同次决策记录中。接入审批系统时，应把决策记录与审批材料一起提供给接手人，供其核查风险、判断已有事实是否还需更新。

付款失败是另一种交接。财务需要看到批准记录、付款指令状态及失败原因。在真实系统中，请求超时可能发生在付款成功之后，只是回执没有返回。应先查询这笔付款的结果或核对账目，再决定是否重试，否则可能给客户付两次款。本地失败样例模拟的是指令创建失败；查询真实支付结果、对账和重试，需要接入支付系统后实现。

## 交付之后如何维护

假设业务部门批准把自动批准上限改为 800 元。程序读取的是 `approve_refund_small.yaml` 的 `approval.threshold_cny`；修改后，500.01 元的 `YF-R-0501` 就会自动批准。但当前检查和界面仍按 500 元设计，还需同步修改：

- 第 5 站的 `approval_threshold_is_500` 检查，以及策略样例 EV-ACTION-003、EV-ADV-006 的预期；
- 工作台、身份和契约说明中的限额文字，并增加 800 元、800.01 元两个边界样例；
- 契约的 `version`，使决策记录中的 `contract_version` 能区分新旧政策。

只改金额参数时，核心策略评估会从 36/36 变成 34/36，因为两条旧样例仍期待超额转人工。更新预期后，还要确认发票、风控与合同客户的处理不变。本仓库的出版基线仍为 500 元，这里说明的是政策变更时需要检查的范围。

交接演练可以安排一次限额变更和一笔付款失败处理。由接管人员运行测试、查找失败原因，再确认是否缺少资料或权限。停用 Agent 时，还要关闭新写入、把未完成任务交给客服或财务，并保留可查询的历史记录，具体见[运行交接](artifacts/10-operations-handoff-and-replication.md)。
