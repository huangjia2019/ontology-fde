# 第 1 站：确定自动退款的业务范围

云帆商城的客服处理退款时，需要在商城、售后、财务和风控系统之间查询，再决定批准、补证或转人工。程序可以按编号关联记录、检查退款条件、生成审批材料；查不到发票时由财务核实，合同客户则由客服核对合同条款。

第一版选择个人客户的小额退款，原因是批准条件可以明确列出，也能用已有样例验证。合同客户的退款可能取决于单独约定，不能直接套用个人客户政策。

## 第一版约定

| 事项 | 本项目的决定 | 对照文件 |
|---|---|---|

| 事实范围 | 金额、履约、发票、工单、风控和证据 | [来源映射](../../config/ontology/source_map.yaml) |
| 候选动作 | 批准小额退款、转人工、请求补充证据 | [动作契约](../../config/actions/) |
| 自动批准条件 | 金额不超过 500 元，且全部相关条件通过 | [批准契约](../../config/actions/approve_refund_small.yaml)、[策略实现](../../src/ontology_fde/policy.py) |
| 暂不自动处理 | 合同客户、发票未知或已开票、黑名单、退款频率异常、已开封耗材超过时限、风控异常、金额超限等 | [退款规则](../../config/rules/refund_rules.yaml)与[实现](../../src/ontology_fde/policy.py) |

## 用金额边界和缺失事实验证范围

```bash
python3 run.py checkpoint 1 --check
python3 run.py run YF-R-0311 --mode draft
python3 run.py run YF-R-0500 --mode write
python3 run.py run YF-R-0501 --mode write
```

347 元的遥控器单发票未知，Draft 建议转人工，尚未创建审批材料。两条 Write 命令中，500 元申请全部条件满足，获批并创建模拟付款指令；500.01 元申请超过上限，创建人工审批材料，等待人工批准。本地没有执行真实支付，指令创建成功还不能确认资金到账。

只用“金额在 500 元以内”的正常申请做测试，会漏掉发票未知时的错误批准。遥控器单补充的正是这项检查。

## 怎样评价业务效果

应分别记录查询耗时、人工核实耗时和等待时间。如果程序减少了客服查询时间，但财务仍需要从头查同样的材料，人工队列的等待可能没有改善。以遥控器单为例，交接时应提供已查的订单、证据与风控结果，让财务先核实缺失的发票状态。这些引用保存在决策记录中，接入审批系统时需一并提供。

自动批准率也需要结合误批、重复付款和漏处理情况看。例如，把 ERP 查不到记录当作已确认未开票，遥控器单会自动通过，虽然开票情况还没核实。本仓库提供判断与执行的样例，不提供生产收益数据。
