# 第 1 站：确定自动退款的业务范围

云帆商城的客服处理退款时，需要在商城、售后、财务和风控系统之间查询，再决定批准、补证或转人工。适合自动化的工作包括关联记录、核对既定条件和生成处理材料。发票无法确认、合同条件不同等情况，仍需交给相应业务人员。

第一版选择个人客户的小额退款，原因是批准条件可以明确列出，也能用已有样例验证。合同客户的退款可能取决于单独约定，不能直接套用个人客户政策。

## 第一版约定

| 事项 | 本项目的决定 | 对照文件 |
|---|---|---|

| 事实范围 | 金额、履约、发票、工单、风控和证据 | [来源映射](../../config/ontology/source_map.yaml) |
| 候选动作 | 批准小额退款、转人工、请求补充证据 | [动作契约](../../config/actions/) |

## 用金额边界和缺失事实验证范围

```bash
python3 run.py checkpoint 1 --check
python3 run.py run YF-R-0311 --mode draft
python3 run.py run YF-R-0500 --mode write
python3 run.py run YF-R-0501 --mode write
```

347 元的遥控器单因为发票未知而转人工；其他条件满足的 500 元样例可以批准；500.01 元样例必须转人工。人工处理的申请，要核实相应条件并获得批准后才能进入付款流程。本地样例生成的是模拟付款指令，真实到账结果还要由支付系统确认。

这三个样例分别验证事实是否完整、金额是否恰好符合上限、金额越界后是否正确转人工。只测试“500 元以内能够批准”，会遗漏发票未知仍被批准的问题。

## 怎样评价业务效果

应分别记录查询耗时、人工核实耗时和等待时间。如果程序减少了客服查询时间，但财务仍需要从头查同样的材料，人工队列的等待可能没有改善。交接材料应包含缺失事实、已查来源和处理建议，使接手人可以继续工作。

自动批准率也需要结合误批、重复付款和漏处理情况看。把未知事实默认为通过，可能提高自动化比例，却增加业务风险。本仓库提供判断与执行的样例，不提供生产收益数据。
