# 第 1 站：跟完“遥控器单”

客户说会议室遥控器无法配对，已经上传视频，申请退款 347 元。申请编号是 `YF-R-0311`。我们先跟着客服把事实找齐，再讨论能否交给 Agent 处理。

## 这笔申请查到了什么

| 业务对象或观测 | 统一编号 | 来源记录 | 能回答的问题 |
|---|---|---|---|
| 客户 | `C-8831` | CRM：`CRM-C-8831` | 谁申请，客户渠道和等级是什么 |
| 订单 | `O-9938` | COMMERCE：`SHOP-ORD-20260701-9938` | 实付多少，是否签收 |
| 订单项 | `OI-9938-1` | COMMERCE：`SHOP-LINE-9938-1` | 退的是哪件商品 |
| 退款申请 | `YF-R-0311` | AFTER_SALES：`AS-RMA-250311` | 申请金额、原因和当前状态 |
| 工单 | `T-0311` | SUPPORT：`ZD-TKT-810311` | 客服已经处理到哪一步 |
| 风控信号 | `RS-7011` | RISK：`RSK-SIG-7011` | 是否需要风控复核 |
| 视频证据 | `EV-0311-1` | EVIDENCE：`OSS-OBJ-A7F2` | 证据是否核验通过 |
| 发票查询 | 查询条件 `order_id=O-9938` | ERP：返回 `not_found` | 本次查询是否找到了发票 |

这些记录各有用途。视频支持“遥控器无法配对”的退款理由，商城记录确认商品与交易，ERP 查询负责提供发票信息。视频充分，不能补齐发票状态。

ERP 本次没有返回发票。可能确实未开票，也可能存在同步延迟或查询范围问题。程序将其保留为 `invoice_status=unknown`，交由财务核实。若直接把空结果填成“未开票”，原本需要核实的申请就可能通过自动审批。

## 自己看一次判断

```bash
python3 run.py inspect YF-R-0311
python3 run.py run YF-R-0311 --mode draft
```

第一条命令返回事实。查看 `source_refs`，找到 ERP 的 `observation: not_found`，再对照 `invoice_status: unknown`。第二条命令返回建议：`queue_human`，命中 `G-INVOICE-UNKNOWN`。此时没有改变退款状态，也没有创建付款指令。

如果继续运行 `write`，程序会创建人工审批材料，状态进入 `pending_human`；它不会替财务把未知改成“确定无发票”。这里所有数据和动作都在本地模拟。

## 财务确认之后还需要做什么

如果财务确认未开票，应补充带来源的确认记录，再重新检查退款条件。如果查到已开票，则先处理发票。两种结论会导致不同的下一步，不能只给 Agent 留一句“财务已看过”。

这个例子说明为什么需要记录查询结果及其来源：下一位处理人要知道缺的是什么，怎样取得这个事实，以及事实补齐后应重新执行哪项检查。
