# 第 10 站：项目组离开之后，谁继续处理

付款指令 PI-0800 创建失败后，财务接到 FMT-0800。接管人员需要通过任务找到退款申请、失败指令和决策记录，核实是否发生付款，再决定继续处理。只看到一句“系统异常”，无法判断是否可以安全重试。

接管人员应知道到哪里查询，由客服还是财务处理，使用什么权限，以及处理后怎样记录结果。

## 本地交接练习

```bash
python3 tools/verify.py
python3 run.py demo --output artifacts/demo
python3 run.py exit-drill
python3 run.py checkpoint 10 --check
```

`demo` 在一次进程中运行 YF-R-0311 的读取、建议和转人工，再运行 YF-R-0500 批准、YF-R-0501 超额转人工、YF-R-0610 风控复核和 YF-R-0800 付款指令创建失败的分支。`manifest.json` 列出生成的文件，可按退款编号关联运行结果、决策记录和对象图，核对本次增加了什么对象、改变了什么状态。

`demo` 重新运行时会重建其输出目录中的示例决策记录。需要保留上一轮对照时，请换一个输出目录。

| 接管工作 | 应能完成的操作 | 建议责任岗位 |
|---|---|---|
| 业务处理 | 判断何时转人工，找到待办及失败原因 | 客服运营、财务 |
| 规则变更 | 找到来源、审核人和回归样例 | 业务规则负责人 |
| 版本发布 | 运行测试，核对变更和回退方案 | 平台工程、测试 |
| 权限维护 | 确认授权范围、变更记录和停用入口 | 安全、系统负责人 |
| 日常复盘 | 从错误判断提取新的回放样例 | 业务与技术共同负责 |

例如，若调整自动批准金额上限，业务负责人先确认风险范围，工程团队修改契约，并同步检查卡、策略样例和工作台说明，测试人员验证新上限及超出一分的结果，发布人员保留回退版本。金额目前还写在多个位置，具体对照见 [FDE 现场练习](../fde-playbook.md)；只改契约，会造成执行结果与检查卡、页面说明不一致。

## 退出演练

业务负责人撤回授权、替代版本接管或发生严重治理问题时，需要停止 Agent，并保证人工还能继续办理。

1. 关闭写入（Close `Write`）：停用新业务写入，保留必要查询。
2. 撤销凭据（Revoke credentials）：确认需要撤销的工作负载身份、密钥和工具授权，由身份管理负责人执行。
3. 交还未完成工作（Return unfinished work to people）：将未完成退款、待人工审批和 `approval_pending_payment` 交给客服或财务。
4. 保留审计证据（Preserve audit evidence）：保留身份版本、权限快照、契约、规则、决策与事故记录。
5. 验证业务连续性（Verify business continuity）：由人工渠道处理一笔测试业务，检查停用主体是否仍有写入。

[`exit-drill`](../../src/ontology_fde/exit_drill.py) 检查的是下表中的配置和文字，不执行上述停用操作：

| 项目 | 程序实际检查的条件 |
|---|---|
| 关闭写入 | [权限配置](../../config/policies/permissions.yaml)的 `production_write` 为 `false`；这个字段记录授权要求，并非已接入生产网关的开关 |
| 撤销凭据 | `security_principal` 以 `workload://` 开头，且本文包含 `Revoke credentials` |
| 移交工作 | [转人工契约](../../config/actions/request_human_refund_approval.yaml)的动作编号为 `request_human_refund_approval`，且本文包含 `Return unfinished work to people` |
| 保留证据 | 身份配置引用 `POL-AUDIT-RETENTION`，且 `audit.py` 文件存在 |
| 业务连续性 | 本文包含 `Verify business continuity`，且转人工契约的第一项效果声明为 `RefundRequest.status -> pending_human` |

`status: PASS` 只说明这些条件成立。输出里的未完成申请数量是样例统计，保留资产清单是程序预设的列表，都没有验证实际移交或归档。真正停用时，系统负责人还要撤销凭据、迁移工单，并通过测试业务确认人工能够继续办理；这个离线命令没有连接 IAM 或 ERP。

## 第二个场景复用哪些东西

假设下一项工作是销售机会跟进，先逐项比较，不直接复制退款规则。

| 可以复用的结构 | 必须重新建模或确认 |
|---|---|
| 来源引用、对象编号映射 | 销售机会、联系人、跟进状态与字段含义 |
| 独立身份和六维权限检查思路 | 新身份、负责人、授权范围与真实凭据 |
| 动作契约、幂等与补偿设计 | 创建跟进任务等实际动作及其后果 |
| 规则来源、草稿审核和边界样例 | 销售判断依据、合同约束与业务案例 |
| 委托信封与冲突记录 | 与法务、风控的委托范围和裁决方式 |
| 决策记录与评估结构 | 新场景预期结果、事故回放和收益指标 |

退款引擎的 Python 代码检查的是退款金额、发票和履约等条件。更换配置名称后，代码仍会执行这些判断，因此新场景需要相应的业务规则和数据适配实现。

以销售跟进为例，来源引用和决策记录结构可以沿用，但“给联系人发消息”需要新的动作契约：联系人是否允许触达、发送过几次、能否撤回。退款的金额上限和发票条件在这里没有意义，必须由新业务的限制替换。
